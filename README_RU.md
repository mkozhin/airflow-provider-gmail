# airflow-provider-gmail

[English](README.md) · [Русский (этот файл)](README_RU.md)

*Powered by [Claude Code](https://claude.ai/code)*

Провайдер Apache Airflow, который находит письма в Gmail по набору условий,
отбирает из них нужные вложения и складывает байты в S3-совместимое хранилище или
на локальный диск. Рассчитан на **Airflow 2.9.1** (`>=2.9,<3`) и **Python 3.10+**.

Ожидается несколько десятков независимых выгрузок, каждая со своими настройками,
поэтому вся повторяющаяся логика уходит в провайдер, а специфика конкретной
выгрузки остаётся параметрами в DAG.

## Что это (и чем не является): три слоя

Сквозная задача «Gmail → вложение → парсинг → хранилище» разбита на три слоя по
**скорости изменений**, а не по объёму кода:

| Слой | Что делает | Стабильность | Где живёт |
|---|---|---|---|
| 1 | Gmail → S3 / локальный диск | одинаков для всех выгрузок | **этот провайдер** |
| 2 | Разбор файла → таблица | самый нестабильный | вне провайдера |
| 3 | Таблица → BigQuery / PostgreSQL / ClickHouse / S3 | уже написан | стандартные провайдеры |

**Этот провайдер — только слой 1. Парсинг файлов в него явно не входит.** Провайдер
знает про Gmail и про то, куда положить байты. Про `.xlsx`, `.csv`, кодировки и
раскладку листов он не знает ничего. Втянуть парсинг внутрь — получить «оператор,
который умеет всё», с комбинаторным взрывом параметров.

Точка стыковки со слоем 2 — файл `_manifest.json`, который провайдер пишет рядом с
вложениями; путь к нему оператор возвращает в XCom. Слой 2 читает манифест и не
интересуется, откуда приехал файл.

### Что решает

- OAuth к Gmail **без хранения короткоживущего `access_token`** и без записи чего-либо
  обратно в метабазу Airflow.
- Корректный разбор MIME: кириллица в именах файлов, вложенные `multipart`,
  inline-картинки.
- В S3-режиме одно и то же письмо **не** скачивается и не отдаётся вниз повторно
  **даже без меток**: манифест с `run_id` плюс `message_id` в пути дают
  дедупликацию доставки сами по себе.
- Ожидание письма (сенсор) вместо падения, когда отчёт ещё не пришёл.

### Состав

```
GmailHook                            # вся нетривиальная логика
GmailAttachmentSensor                # есть ли подходящее письмо? (только Gmail)
  └─ GmailAttachmentToS3Sensor       # + bucket/prefix: есть ли письмо БЕЗ манифеста?
GmailAttachmentsBaseOperator         # абстрактный: поиск, отбор, манифест, метка
  ├─ GmailAttachmentsToS3Operator    # + bucket/prefix/aws_conn_id, dedup, overwrite
  └─ GmailAttachmentsToLocalOperator # + path, без dedup, всегда перезаписывает
```

S3-оператор работает с любым S3-совместимым хранилищем (Yandex Object Storage,
MinIO, …), не только с AWS — укажите у нижележащего Amazon-подключения свой
`endpoint_url` через `extra`.

## Заведение Connection

Connection **read-only**. На каждый запуск хук делает refresh-grant в память и
строит свежий сервис Gmail; `access_token` нигде не сохраняется. Запись
обновлённого токена обратно в Connection дала бы гонки между параллельными
задачами, потребовала бы прав на запись в метабазу и приводила бы к загадочным
401. Цена — один лишний HTTP-запрос на задачу.

```
conn_type: gmail
login:     <client_id>       # на форме — «Client ID»
password:  <client_secret>   # на форме — «Client Secret»
extra:     {"refresh_token": "1//09fy...",
            "user_id": "me",
            "scopes": ["https://www.googleapis.com/auth/gmail.readonly"]}
```

- **`client_id` / `client_secret`** берутся у OAuth-клиента типа *installed*
  (создаётся в консоли Google Cloud для вашего проекта). Кладутся в `login` /
  `password`, на форме переименованы в *Client ID* / *Client Secret*.
- **`refresh_token`** берётся **один раз**, из token-файла, полученного при первом
  прохождении OAuth-консента (например, через `google-auth-oauthlib`). Используется
  только `refresh_token`; `access_token`/`expiry` из файла игнорируются. На форме
  `refresh_token` — **password-поле**: он долгоживущий и секретный, показывать
  открытым текстом нельзя.
- **Почему `access_token` не нужен.** Обновлённый токен, который хук получает каждый
  запуск, несёт ровно те права, что выданы при консенте; сохранённый access-токен
  был бы лишь устаревшей копией и источником гонок (см. выше).
- **`user_id`** (дефолт `"me"`) — **обязательный** `userId` каждого вызова Gmail
  API; читается из `extra.user_id`.
- **Поле `scopes` в `extra` справочное / декоративно.** Обновлённый токен несёт ровно
  те права, что были выданы `refresh_token` при консенте; правка `scopes` в
  Connection ничего не меняет. Поле нужно как документация для человека. Реальная
  проверка прав — 403 `insufficientPermissions` при `batchModify`.

Для проставления меток (`mark_processed=True`) нужен скоуп `gmail.modify`. Расширить
права существующего `refresh_token` **нельзя** — его придётся перевыпустить, заново
пройдя OAuth-консент с выданным `gmail.modify`.

> ## ⚠️ OAuth-приложение ДОЛЖНО быть «In production»
>
> Если consent screen проекта остался в статусе **«Testing»**, Google выдаёт
> `refresh_token` со сроком жизни всего **7 дней**. Пайплайн отработает неделю и
> затем **молча сломается** — это самая частая ловушка данной схемы. Опубликуйте
> OAuth-приложение (статус **«In production»**), прежде чем на него полагаться.
>
> Отозванный или истёкший `refresh_token` даёт понятное исключение `GmailAuthError`
> с подсказкой, а не сырой `RefreshError`.

## Параметры

### Параметры операторов

`GmailAttachmentsToS3Operator` и `GmailAttachmentsToLocalOperator` разделяют
базовые параметры ниже и каждый добавляет свои.

**Общие (базовый оператор):**

| Параметр | Тип | Дефолт | Смысл |
|---|---|---|---|
| `source` | `str` | *обязателен* | Свободная метка для трассировки; пишется в манифест `source`. В путь не входит. |
| `gmail_conn_id` | `str` | `"gmail_default"` | Read-only Gmail Connection. |
| `query` | `str \| None` | `None` | Сырая строка поиска Gmail. **Если задана — структурированные поля ниже игнорируются** (два источника истины недопустимы). Templated. |
| `from_email` | `str \| None` | `None` | Структурированный фильтр → Gmail `from:`. Templated. |
| `subject_contains` | `str \| None` | `None` | Структурированный фильтр → Gmail `subject:`. Templated. |
| `has_attachment` | `bool` | `False` | `True` → добавляет `has:attachment`. `False` не добавляет ничего (`-has:attachment` не подставляется никогда). |
| `filename_contains` | `str \| None` | `None` | Структурированный фильтр → Gmail `filename:` (только грубое сужение на сервере — см. «Подводные камни»). Templated. |
| `attachment_pattern` | `str \| None` | `None` | `re.search` по **декодированному** имени. `None` → подходит любое не-inline вложение. **Не templated** (ADR-0005): битая регулярка падает на парсинге DAG. |
| `lookback_days` | `int` | `7` (S3) / `0` (local) | Скользящее окно `after:` в календарных днях от полуночи опорного дня. `0` → только сегодня; `7` → восемь календарных дней. |
| `mark_processed` | `bool` | `False` | Вешать Gmail-метку на обработанные письма (нужен `gmail.modify`). По умолчанию выключено → хватает `gmail.readonly`. |
| `label_suffix` | `str \| None` | `None` | `None` → метка `airflow/processed`; `"avito"` → `airflow/processed/avito`. |
| `timezone` | `str` | `"Europe/Moscow"` | Зона для дня окна, партиции `dt=` и `internal_date` в манифесте. |
| `date_from` / `date_to` | `str \| None` | `None` | Явный диапазон backfill `YYYY-MM-DD` (ADR-0004), обычно из `dag_run.conf`. Если задан хоть один — `lookback_days` игнорируется. Templated. |

**`GmailAttachmentsToS3Operator` добавляет:**

| Параметр | Тип | Дефолт | Смысл |
|---|---|---|---|
| `bucket` | `str` | *обязателен* | Целевой бакет. |
| `prefix` | `str` | `""` | Базовый префикс ключа, например `gmail/avito`. **Один префикс = одна выгрузка** (ADR-0003). Templated. |
| `aws_conn_id` | `str` | `"aws_default"` | Amazon/S3 Connection (может указывать на свой `endpoint_url`). |
| `overwrite` | `bool` | `False` | `True` → принудительная перекачка; манифест даже не читается. Несовместим с `GmailAttachmentToS3Sensor` (см. «Ограничения»). |

**`GmailAttachmentsToLocalOperator` добавляет:**

| Параметр | Тип | Дефолт | Смысл |
|---|---|---|---|
| `path` | `str` | *обязателен* | Базовый каталог, например `/data/gmail/avito`. Templated. |

Обратите внимание: `lookback_days` здесь по умолчанию `0` (а не `7`), и **публичного
аргумента `overwrite` нет** — локальный оператор всегда перезаписывает.

### Параметры сенсоров и когда какой брать

Оба сенсора точно повторяют фильтрующие параметры оператора (`query`, `from_email`,
`subject_contains`, `has_attachment`, `filename_contains`, `attachment_pattern`,
`lookback_days`, `timezone`, `date_from`/`date_to`, `mark_processed`,
`label_suffix`, `source`, `gmail_conn_id`), чтобы искать тот же набор писем, что и
оператор. Дополнительно доступны ручки `BaseSensorOperator`:

| Параметр | Тип | Дефолт | Смысл |
|---|---|---|---|
| `mode` | `str` | `"reschedule"` | **Выставляется `reschedule` по умолчанию в `__init__`** — в режиме `poke` сенсор держит слот воркера всё время ожидания (часы); при десятках выгрузок это выест пул. |
| `poke_interval` | `int` | `60` | Секунды между poke (на практике ~30 мин). |
| `timeout` | `int` | — | Время до сдачи. |
| `soft_fail` | `bool` | `False` | `True` → таймаут даёт `skipped` (зелёный DAG); `False` → падение + алерт. Наследуется от `BaseSensorOperator`. |

`GmailAttachmentToS3Sensor` дополнительно принимает `bucket`, `prefix` (дефолт `""`)
и `aws_conn_id` (дефолт `"aws_default"`).

**Какой сенсор брать:**

- **`GmailAttachmentSensor`** — *«есть ли подходящее письмо?»* Смотрит только в
  Gmail; `poke()` → `True`, когда поиск непуст. Пригоден там, где дедупликацию
  обеспечивает сам Gmail (`mark_processed=True`, метка убирает обработанные из
  выдачи), и как **основной сенсор для локального оператора**. В паре с локальным
  оператором **задайте одинаковый `lookback_days` у обоих** (у сенсора дефолт `7`,
  у локального оператора — `0`), иначе сенсор может сработать на письме, которое
  более узкое окно оператора не вернёт, и DAG зависнет. **Не** полагайтесь на
  `lookback_days=1` для дедупа — обработанное письмо остаётся в выдаче до конца окна,
  и при выключенных метках этот сенсор срабатывает повторно, а оператор за ним честно
  скипается.
- **`GmailAttachmentToS3Sensor`** — *«есть ли новая работа?»* Наследует первый,
  добавляет `bucket`/`prefix`/`aws_conn_id` и отбрасывает каждое письмо, у которого
  уже есть `_manifest.json` в S3. `True` только если осталось хотя бы одно
  **необработанное** письмо. Это естественный гейт для `GmailAttachmentsToS3Operator`
  — берите его для штатной регулярной S3-выгрузки.

## Ограничения

- **Один воркер на одном сервере.** Провайдер написан в расчёте на один воркер на том
  же сервере. `GmailAttachmentsToLocalOperator` пишет на локальный диск, не
  разделяемый между воркерами.
- **Локальный оператор + несколько воркеров.** На CeleryExecutor с несколькими
  воркерами или на KubernetesExecutor задача скачивания и задача парсинга могут
  уехать на разные машины, и парсинг не найдёт файл. В таком окружении локальный
  оператор безопасен только *внутри одной задачи*; для всего остального — S3.
- **Дедупликация доставки есть только в S3-режиме**, по манифесту + `run_id`.
  Локальный оператор состояния дедупа не хранит (`_read_manifest` всегда `None`) и
  повторно отдаёт вниз каждое найденное письмо каждый запуск — by design.
- **Метки требуют `gmail.modify` + перевыпуска токена.** Расширить права существующего
  `refresh_token` нельзя; перевыпустите его через OAuth-консент с выданным
  `gmail.modify`.
- **В S3-режиме `-label:` НЕ используется как фильтр поиска** (ADR-0001). Проставление
  метки (`batchModify`) и запись return-XCom не атомарны: если метка уже проставлена,
  а задача упала до возврата, поиск с `-label:` не нашёл бы письмо, его манифест
  текущего `run_id` не дошёл бы до решения о дедупе, и полностью скачанное письмо тихо
  пропало бы при зелёном retry. Поэтому в S3 корректность держит **только** манифест +
  `run_id`; `mark_processed=True` может всё ещё *вешать* метку как внешний маркер, но
  на поиск она не влияет. В **локальном** режиме метка — опт-ин дедуп для широких окон
  (`mark_processed=True` подмешивает `-label:` в поиск) с честной оговоркой, что
  падение между проставлением метки и доставкой может «потерять» письмо на retry —
  именно поэтому в S3 так не делают.
- **`overwrite` несовместим с `GmailAttachmentToS3Sensor`.** Storage-aware сенсор
  отбрасывает письма, у которых уже есть манифест, и вернёт «работы нет» — оператор за
  ним не запустится. Запускайте overwrite-backfill **без** этого сенсора — вручную или
  из отдельного backfill-DAG без сенсора (см. `example_gmail_s3_backfill.py`).
- **Параллельные запуски требуют `max_active_runs=1`.** Проверка манифеста — это
  check-then-act (`_read_manifest` → запись); два пересекающихся `DagRun` одной
  выгрузки могут оба не увидеть манифест и оба скачать и отдать одно письмо. «Один
  сервер» ≠ «один активный запуск». Гарантия формулируется честно: **нет повторов при
  последовательных запусках**; от параллельных защищает DAG через `max_active_runs=1`
  (выставлено и прокомментировано в примерах).
- **Один префикс = одна выгрузка (ADR-0003).** Две выгрузки на общий `prefix` в одном
  бакете, с пересекающимися письмами из одного ящика, тихо затирают друг другу
  манифест. Изоляции путей между выгрузками нет — давайте каждой выгрузке свой
  `prefix`.
- **Локальный дефолт `lookback_days=0` против S3-дефолта `7` (ADR-0001).** S3
  дедуплицирует доставку, поэтому широкое окно там безопасно; локальный оператор — нет,
  поэтому широкое окно повторно доставляет каждое письмо каждый запуск. Безопасный
  локальный дефолт — `0` (только сегодня): дубли подавляются *узостью окна*, а не
  дедупом.

## Подводные камни Gmail

- **`filename:` — не поиск по подстроке.** Gmail токенизирует имя по разделителям, а
  не ищет подстроку: `filename:report` найдёт `annual-report-2024.xlsx`, но **не**
  `myreport.xlsx`. Регулярок и wildcard в поиске Gmail нет. `filename_contains` — лишь
  грубое сужение на сервере; точный отбор — `attachment_pattern` (`re.search`).
- **`has:attachment` считает inline-картинки.** Логотип в подписи (`image001.png`) —
  тоже вложение. Провайдер оставляет только части с непустым `filename` и выкидывает
  часть **только** если она inline *и* `mime_type` начинается с `image/`.
  Inline-PDF/xlsx остаются (`Content-ID` их не понижает); от лишнего защищает
  `attachment_pattern`.
- **Вложенные метки не иерархичны при поиске.** `label:airflow/processed` **не**
  находит письмо, помеченное только `airflow/processed/avito`. Поэтому в `-label:`
  подставляется ровно та же итоговая строка (всегда в кавычках), которую вешаем.
- **`attachmentId` нестабилен** между запросами — используется сразу после
  `messages.get` и нигде не сохраняется.
- **Имена файлов приходят уже декодированными.** Gmail отдаёт
  `MessagePart.filename` готовой UTF-8-строкой (кириллическое `Отчёт за июль.xlsx`,
  а не сырой `=?UTF-8?B?...?=` из заголовка `Content-Disposition`), поэтому
  провайдер **не** декодирует имена по RFC 2047/2231 — только санитизирует путь.
  Это подтверждено на фикстурах из Task 2. Декодируются по RFC 2047 только
  `Subject`/`From` (читаются из `payload.headers`) — там encoded-words есть всегда.
- **Текстовый `after:` трактуется в таймзоне Gmail**, а не вашей, и граница окна
  уезжает. Провайдер всегда отдаёт **числовой** `after:<epoch>` (и `before:<epoch>`),
  вычисленный от полуночи опорного дня в `timezone` оператора, — без места для
  толкований.

## Контракт `_manifest.json` (стык со слоем 2)

Манифест — контракт со следующим слоем, поэтому его схема одинакова в плане, в
`docs/gmail-pipeline-layers-2-3.md`, в `manifest.py` и здесь:

```json
{"source": "avito",
 "message_id": "18c2f4a9b3d5e6f7",
 "internal_date": "2026-07-10T09:14:22+03:00",
 "subject": "Отчёт за 09.07",
 "from": "reports@avito.ru",
 "run_id": "scheduled__2026-07-10T06:00:00+00:00",
 "files": [{"name": "report.xlsx", "size": 148223,
            "path": "gmail/avito/dt=2026-07-10/18c2f4a9b3d5e6f7/report.xlsx"}]}
```

- `source` — свободная метка для трассировки, в путь не входит.
- `message_id` — опаковый id письма в пределах ящика (`users.messages.list` → `id`),
  hex-строка, безопасна для пути. Не путать с RFC-заголовком `Message-ID` и с
  `attachmentId`.
- `internal_date` — ISO 8601 в `timezone` оператора (по умолчанию `+03:00`).
- `subject` / `from` — декодированы из RFC 2047 (кириллическая тема приходит как
  `=?UTF-8?B?...?=`).
- `run_id` — `DagRun`, записавший манифест. Слой 1 по нему отличает «доставлено
  прошлым запуском» (вниз не отдавать) от «записано упавшей попыткой этого же запуска»
  (отдать, не качая). **Слой 2 это поле игнорирует.**
- `files[].name` — исходное имя вложения до санитизации.
- `files[].size` — фактическое число записанных байт (`len(data)` после декодирования).
- `files[].path` — **канонический** путь назначения: для S3 — ключ внутри `bucket`
  (`<prefix>/dt=…`), для локального — абсолютный путь на диске. Поля `s3_key` **нет** —
  слой 2 не должен знать, откуда приехал файл.

Манифест всегда пишется **последним**, после всех вложений письма, — его наличие
доказывает, что вложения записаны. Битый/невалидный манифест даёт громкий
`ManifestError`, а не тихий пропуск.

## Что уходит в XCom

Оператор возвращает **только канонические пути к манифестам** писем, обработанных
**в этом запуске**, — ничего больше.

- `bucket` и `aws_conn_id` в XCom **намеренно не** кладутся. Следующая задача (если она
  есть) берёт их из своих параметров: `conn_id` у неё обычно тот же, а бакет — как
  правило `Variable`, заданная сверху DAG и переданная во все задачи.
- Структурированный URI или объект не вводится — это преждевременная универсализация
  под слой, которого может ещё и не быть.

## Примеры DAG

См. `example_dags/`:

- **`example_gmail_to_s3.py`** — штатная ежедневная выгрузка:
  `GmailAttachmentToS3Sensor` → `GmailAttachmentsToS3Operator` → заглушка парсинга,
  `mark_processed=False`, `max_active_runs=1` (с комментарием про гонку
  check-then-act). Обычный `GmailAttachmentSensor` здесь использовать **нельзя** — при
  выключенных метках он сработает повторно на уже обработанном письме.
- **`example_gmail_to_local.py`** — скачивание → парсинг → уборка (`all_done`), с явным
  упоминанием ограничения по воркерам и отсутствия идемпотентности.
- **`example_gmail_s3_backfill.py`** — ручное переигрывание с `overwrite=True` и **без**
  `GmailAttachmentToS3Sensor` (сенсор увидел бы манифест и не пустил бы оператор),
  `date_from`/`date_to` заполняются из `dag_run.conf` (ADR-0004).

## Установка

```bash
pip install airflow-provider-gmail          # Gmail-хук, локальный оператор, Gmail-сенсор
pip install "airflow-provider-gmail[s3]"    # + S3-оператор и storage-aware сенсор
```

Extra `s3` подтягивает `apache-airflow-providers-amazon`; S3-части импортируют его
лениво, поэтому хук, локальный оператор и `GmailAttachmentSensor` работают и без него.
