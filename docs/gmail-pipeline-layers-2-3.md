# Gmail → DWH: слои 2 и 3 (парсинг и загрузка)

Отложенные размышления. Слой 1 (`airflow-provider-gmail`) спроектирован и уходит
в реализацию отдельно; здесь зафиксировано то, к чему нужно вернуться потом.

Дата обсуждения: 2026-07-10.

## Общая декомпозиция

Задача «Gmail → вложение → парсинг → хранилище» разбита на три слоя с разной
скоростью изменений. Границы проведены именно по ней, а не по объёму кода.

| Слой | Что делает | Стабильность | Где живёт |
|---|---|---|---|
| 1 | Gmail → S3 / локальный диск | одинаков для всех выгрузок | `airflow-provider-gmail` |
| 2 | Разбор файла → таблица | самый нестабильный | вне провайдера (см. ниже) |
| 3 | Таблица → BQ / PG / CH / S3 | уже написан до нас | стандартные провайдеры + тонкая обёртка |

Ключевое решение: **парсинг не входит в Gmail-провайдер.** Провайдер знает про
Gmail и про то, куда положить байты. Про `.xlsx` он не знает ничего. Иначе
получается «оператор, который умеет всё», с комбинаторным взрывом параметров.

## Точка стыковки слоёв 1 и 2

Слой 1 пишет рядом с вложениями `_manifest.json` и возвращает в XCom список
путей к манифестам. Слой 2 читает манифест и не интересуется, откуда файл
приехал — из Gmail, из S3, с диска.

```json
{"source": "avito", "message_id": "18c2f4a9b3d5e6f7",
 "internal_date": "2026-07-10T09:14:22+03:00",
 "subject": "Отчёт за 09.07", "from": "reports@avito.ru",
 "run_id": "scheduled__2026-07-10T06:00:00+00:00",
 "files": [{"name": "report.xlsx", "size": 148223,
            "path": "gmail/avito/dt=2026-07-10/18c2f4a9b3d5e6f7/report.xlsx"}]}
```

Схема — единая с планом слоя 1, менять её можно только в обоих документах сразу:

- `path` — канонический путь назначения (S3-ключ либо абсолютный путь на диске).
  Поля `s3_key` нет: слой 2 не должен знать, откуда приехал файл.
- `internal_date` — ISO 8601 в таймзоне оператора (по умолчанию `Europe/Moscow`).
- `name` — исходное имя вложения до санитизации.
- `run_id` — `DagRun`, записавший манифест; используется слоем 1 для дедупликации,
  слой 2 поле игнорирует.

Манифест выполняет двойную роль: описание скачанного для слоя 2 и (в S3-варианте)
состояние для дедупликации в слое 1 — по `run_id` слой 1 отличает уже доставленные
письма от свежих. Локальный диск состояние не хранит и файлы перезаписывает.

Про идемпотентность слоя 3: в S3-режиме слой 1 сам не отдаёт письмо вниз повторно,
поэтому строгая идемпотентность загрузки не обязательна. Но `overwrite=True`,
ручное переигрывание и локальный режим повторы допускают, так что перезаписываемая
партиция за день всё равно предпочтительнее слепого append.

## Слой 2: парсинг

### Главное ограничение

**DataFrame нельзя передать через XCom** — XCom живёт в метабазе Airflow. Значит:

- либо слой 2 пишет результат в staging (parquet/jsonl в S3), а в XCom кладёт ключ;
- либо слои 2 и 3 — одна задача, и DataFrame передаётся из функции в функцию.

Развилка не закрыта. Склоняемся к staging: он даёт переигрывание слоя 3 без
повторного парсинга и точку для проверки данных глазами.

### Где живёт код разбора — три варианта, решение не принято

1. **Хелпер + `@task` в DAG** (склоняемся сюда). Общая библиотека даёт
   `read_manifests()` и `read_table()`: скачать по манифесту, определить формат
   по расширению, разобраться с кодировкой и разделителем CSV, открыть `.xls`
   старым движком, `.xlsx` — новым. Вся специфика (шапка на третьей строке,
   лист «Данные», переименование колонок, типы) — обычный python в DAG.
2. **`ParseTabularOperator` с параметрами** `sheet_name`, `header_row`,
   `skip_rows`, `rename_columns`, `dtypes` + `transform` как callable-люк.
   Единообразно, конфигурируется из YAML. Риск: набор полей будет расти.
3. **Чистый pandas в каждом DAG.** Копипаста бойлерплейта в тридцати местах.

Аргумент против преждевременного выбора: пока не скачаны первые пять реальных
файлов от реальных клиентов, любой дизайн парсинга — угадывание. Именно там
вылезут двойные шапки, объединённые ячейки и даты строками.

### Что точно понадобится

- `.xlsx` → `openpyxl`, `.xls` → `xlrd`, `.csv` → определение кодировки
  (cp1251 встречается) и разделителя (`;` в русских выгрузках).
- Кириллица в именах файлов и темах писем — везде.
- Люк для кода на нестандартные файлы, каким бы ни был выбранный вариант.

## Слой 3: загрузка

Требования из исходной постановки:

- **BigQuery / PostgreSQL / ClickHouse** — через стандартные провайдеры.
- **S3-совместимое хранилище** (не AWS, endpoint через `extra` у `S3Hook`):
  - целиком файлом в `json` / `jsonl`;
  - либо с разбивкой по hive-партициям (`dt=YYYY-MM-DD/`).
- Данные за прошлые дни нужно **обновлять** (перезапись партиции) или
  **дописывать новые файлы рядом** — режим задаётся настройкой.

### Открытые вопросы

- `append` vs `overwrite` партиции: кто решает и как выражается в конфиге.
- Идемпотентность загрузки: если она есть (`REPLACE` партиции за день), то
  повторная обработка письма в слое 1 безвредна — а значит требования к
  дедупликации в слое 1 можно ослабить.
- Нужен ли staging-слой между 2 и 3 (см. выше).
- Схема таблицы: выводится из файла или задаётся явно? Что делать, когда
  клиент добавил колонку.

## Фабрика DAG'ов

Выгрузок ожидается несколько десятков. Обсуждалась генерация DAG'ов из
YAML-конфигов (фильтр писем, фильтр вложений, описание парсинга, цель) с
`transform: my_transforms:fix_headers` как ссылкой на python-функцию для
нестандартных файлов. К этому имеет смысл возвращаться после того, как
руками написаны первые три-пять DAG'ов и видно, что в них реально общего.
