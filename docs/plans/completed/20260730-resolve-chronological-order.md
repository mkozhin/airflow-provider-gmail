# `pick="all"` сортирует вложения по времени письма (`internal_date`), а не по порядку входного списка

## Обзор

`GmailResolveAttachmentsOperator`/`resolve_attachments()` с `pick="all"` сейчас
отдают вложения **в порядке входного списка `manifests`** (`resolve.py:73-77`,
докстринг: *"in input order"*) — то есть в порядке, в котором Gmail API вернул
письма при поиске / в порядке, в котором download-оператор их обработал. Это
**не** хронологический порядок по времени письма: сам Gmail не гарантирует
`messages.list` в хронологическом порядке, и код никак не сортирует результат.
Проверено эмпирически (`_resolve()` с манифестами вразнобой по времени —
результат идёт строго по входному списку, не по датам).

**Что делаем.** `pick="all"` начинает сортировать письма по возрастанию
`internal_date` (Gmail-овское время получения письма, уже хранится в каждом
`_manifest.json` — `manifest.py:76`) — самое старое письмо первым. Одинаковый
`internal_date` (включая дублирующийся манифест на входе) разрешается стабильной
сортировкой — порядок между такими манифестами остаётся как во входном списке.
Файлы **внутри** одного манифеста (`files[]`) не переупорядочиваются.
`pick="latest"` не меняется.

**Бенефит:** downstream-потребитель (`airflow-provider-tablefile` и т.п.),
получив список путей через XCom, обрабатывает их в реальном хронологическом
порядке писем, а не в артефактном порядке ответа Gmail API/скачивания.

**Важно:** данных для этого достаточно уже сейчас — `internal_date` обязательное
поле манифеста с самого начала (Task 2c), новый вызов Gmail API не нужен, схема
манифеста не меняется.

## Development Approach

- **testing approach**: Regular (сначала код, потом тесты).
- Менять только ветку `pick == "all"` в `_resolve()`; `pick == "latest"` и
  публичные сигнатуры не трогать.
- Tie-break — **стабильная сортировка** (`sorted()` в Python гарантированно
  стабилен), без явного вторичного ключа по `message_id`. **Пересмотрено и
  подтверждено после двух раундов ревью (codex + planning:plan-review):** оба
  указали, что при таком tie-break письма с одинаковым `internal_date`
  всё равно упорядочены по входному списку — тому самому "артефакту", который
  меняем. Решение пользователя — оставить как есть: `internal_date`
  хранится с точностью до миллисекунды (см. `Technical Details`/ADR-0008), и
  вероятность двух реальных писем с идентичной меткой практически нулевая;
  остаточная недетерминированность — осознанный и задокументированный в
  ADR-0008 trade-off, а не дефект.
- **CRITICAL: каждая задача включает тесты**, все тесты зелёные перед
  следующей задачей.
- Обратная совместимость: **сознательно ломается** порядок вывода `pick="all"`
  (BREAKING) — сигнатуры, схема манифеста и `pick="latest"` не меняются.

## Testing Strategy

- **unit tests** (`pytest`, мок на уровне `googleapiclient`/`fake_s3` — сеть не
  трогаем; для `resolve.py` тесты строят `Manifest`-фикстуры напрямую, без
  моков вообще):
  - `pick="all"` с манифестами **вразнобой по датам** на входе → результат
    отсортирован по возрастанию `internal_date`, независимо от входного
    порядка (аналог ручной проверки из брейнсторма: вход `[B(11:00), A(10:00),
    C(09:00)]` → выход `[C, A, B]`). **Уточнено codex-ревью:** этот кейс
    обязан использовать **разные UTC-offset'ы** (не только разное время при
    одинаковом offset), иначе тест пройдёт и при ошибочной лексикографической
    сортировке ISO-строк, а не по фактическому моменту времени — по образцу
    уже существующего `test_latest_uses_instant_not_lexicographic_order`
    (`tests/test_resolve.py:97-107`, где текст ISO лексикографически сортирует
    в одну сторону, а реальный момент времени — в другую).
  - **Стабильный tie-break**: два манифеста с одинаковым `internal_date` →
    порядок между ними сохраняется как во входном списке (проверить на обеих
    перестановках входа). Это единственный тест на стабильность tie-break —
    отдельная проверка на **дубле** одного и того же манифеста не нужна
    (см. ниже).
  - **Дубль одного манифеста на входе** (тот же `message_id`/`internal_date`
    дважды) → обе копии остаются в результате. **Уточнено codex-ревью:**
    существующий `test_all_keeps_duplicates` уже проверяет это (количество
    копий); "относительный порядок" между двумя **идентичными** записями
    физически ненаблюдаем (они неразличимы), так что расширять этот тест на
    порядок незачем — стабильность tie-break уже покрыта тестом на **разных**
    манифестах с одинаковым `internal_date` выше.
  - **Перегруппировка дублей — новый наблюдаемый побочный эффект** (найдено
    `planning:plan-review`): раньше **вперемешку** расположенные дубли
    сохраняли позиции (`[A, B, A]` → `[A, B, A]`); теперь сортировка по дате
    их **группирует** — при `internal_date(A) < internal_date(B)` результат
    станет `[A, A, B]`. README.md/README_RU.md/`CONTEXT.md:74-75` обещают
    "дубликаты проходят как есть" — это остаётся верным по **количеству**, но
    не по **позиции**; нужен тест на вход `[A, B, A]` (несмежные дубли) и
    явная строчка в докстринге/ADR-0008/CHANGELOG про перегруппировку.
  - **Пин нового порядка на публичном крае** (найдено `planning:plan-review`):
    все новые проверки в этой задаче бьют по чистому `_resolve()`; существующие
    facade/operator-тесты (`test_mixed_s3_and_local_manifests_resolve_in_one_call`,
    `test_logs_summary_and_each_path`) специально не трогаются, потому что их
    входные данные уже хронологические — значит, ничего не фиксирует новую
    гарантию на уровне `resolve_attachments()`/XCom/лога. Решение: **перевернуть
    входной порядок** в обоих тестах (сохранив хронологический ожидаемый
    результат) — ноль новых тестов, но теперь регресс сортировки между
    `_resolve()` и публичным краем будет пойман.
  - **Файлы внутри одного манифеста не переупорядочиваются** — порядок
    `files[]` сохраняется как в манифесте, сортируются только манифесты между
    собой.
  - **Малформед `internal_date`** (naive-строка без offset) при `pick="all"` →
    `ValueError` из `from_local_iso` пробрасывается (новое поведение — раньше
    `pick="all"` вообще не парсил `internal_date`).
  - `pick="latest"` — существующие тесты должны остаться зелёными без правок
    (поведение не меняется).
  - Обновить/переименовать `test_all_flattens_in_input_order` → тест на
    хронологический порядок (входной порядок эту гарантию для "all" больше не
    описывает).
  - Прогнать `tests/test_operator_resolve.py` целиком — операторные тесты не
    должны сломаться (входные данные там уже хронологические, но нужна
    фактическая зелёная проверка, не только по чтению кода).
- **e2e**: нет — неприменимо (чистая функция + оператор без сети в тестах).
- Полный `pytest` + `pytest --cov=airflow_provider_gmail --cov-report=term-missing`
  ≥ 99% (текущий уровень покрытия проекта).

## Solution Overview

В `_resolve()` ветка `pick == "all"` перед `extend()` сортирует `pairs` по
`from_local_iso(manifest.internal_date)` (тот же парсер, что уже использует
`pick="latest"`), затем разворачивает в файлы в этом новом порядке — без
изменений `_attachment_paths()`, `resolve_attachments()`, схемы манифеста или
`pick="latest"`.

## Technical Details

- `_resolve()`, ветка `"all"` (было):
  ```python
  if pick == "all":
      result: list[str] = []
      for manifest_path, manifest in pairs:
          result.extend(_attachment_paths(manifest_path, manifest))
      return result
  ```
  станет:
  ```python
  if pick == "all":
      ordered = sorted(pairs, key=lambda pair: from_local_iso(pair[1].internal_date))
      result: list[str] = []
      for manifest_path, manifest in ordered:
          result.extend(_attachment_paths(manifest_path, manifest))
      return result
  ```
  `sorted()` — стабильная сортировка Python, повторяет гарантию tie-break без
  дополнительного кода. **Побочный эффект (найдено `planning:plan-review`):**
  сортировка **перегруппирует** вперемешку расположенные дубли одного и того
  же манифеста — раньше `[A, B, A]` оставался `[A, B, A]`, теперь при
  `internal_date(A) < internal_date(B)` станет `[A, A, B]`. Задокументировать
  это явно (докстринг `_resolve`, ADR-0008, CHANGELOG) — см. Testing Strategy.
- **Конвенция проекта — инлайн-цитаты ADR** (найдено `planning:plan-review`,
  проверено: `resolve.py:28` цитирует ADR-0001, `README.md`/`CONTEXT.md`
  цитируют ADR-0001..0007 по всему тексту). Все докстринги/README/README_RU/
  CONTEXT.md, которые правит этот план, должны получить `(ADR-0008)` — иначе

### Task 3: ADR-0008 — хронологическая сортировка `pick="all"`

**Files:**
- Create: `docs/adr/0008-resolve-all-sorts-by-internal-date.md`

- [x] Написать ADR-0008 в стиле существующих (`docs/adr/0007-*.md`): Статус
      (Accepted), Дата (2026-07-30), Контекст (текущий "in input order",
      почему это не совпадает с хронологией писем — Gmail не гарантирует
      порядок `messages.list`), Решение (сортировка по возрастанию
      `internal_date`, стабильный tie-break, `pick="latest"` не меняется),
      Обоснование (данные уже есть в манифесте, минимальность изменения),
      **по образцу ADR-0007 ("Рассматривались четыре варианта: …",
      `docs/adr/0007-*.md:13-14`) разобрать отклонённые альтернативы**
      (найдено вторым прогоном `planning:plan-review` — раньше ADR разбирал
      только альтернативу tie-break, не сам выбор ломать контракт):
      - **Опциональный флаг сортировки** (например `sort_by_date=True`),
        сохраняющий старое поведение `pick="all"` по умолчанию — отклонён:
        плодит комбинации `pick`×`flag`, а старое поведение ("в порядке
        входного списка") не имеет ни одного обоснованного случая
        использования, который стоило бы сохранять
      - **Новый режим `pick`** (например `pick="all_by_date"`) — отклонён:
        два способа получить "все вложения" — источник путаницы, а не
        польза; хронологический порядок должен быть *единственно
        разумным* значением по умолчанию для `"all"`
      - **Сортировка на стороне потребителя** (downstream DAG сортирует сам
        по `internal_date` из манифеста) — отклонена: заставляет каждого
        потребителя дублировать логику, которая и так уже есть в резолвере
        (он читает манифесты и знает `internal_date`), нарушая роль
        резолвера как единственного клиента контракта манифеста
      - Итог: прямой BREAKING выбран как единственно оправданный —
        pre-1.0 провайдер, единственный реальный кейс использования
        (хронологический порядок), прецедент `[0.3.0]` (там XCom-контракт
        уже ломали без флага защиты)
      - **Явно разобрать альтернативу tie-break по `message_id`** (симметрично
        `pick="latest"`, `resolve.py:84`) — рассмотрена и отклонена в двух
        раундах ревью (codex + `planning:plan-review`) и подтверждена
        пользователем: `internal_date` хранится с точностью до миллисекунды
        (`to_local_iso`/`from_local_iso`), вероятность двух разных писем с
        идентичной меткой практически нулевая — остаточная
        недетерминированность стабильной сортировки при коллизии дат
        (порядок в этом крайнем случае определяется входным списком) —
        осознанный, принятый trade-off, а не забытый случай
      Consequences (BREAKING для существующих потребителей `pick="all"`; новый
      источник `ValueError` на битом `internal_date`; **перегруппировка
      вперемешку расположенных дублей** одного манифеста — раньше `[A, B, A]`
      оставался как есть, теперь группируется по дате, например `[A, A, B]`)
