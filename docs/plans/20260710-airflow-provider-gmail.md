# Airflow-провайдер `airflow-provider-gmail`

## Overview

Провайдер для Airflow 2.9.1, который находит письма в Gmail по заданным условиям,
отбирает из них нужные вложения и складывает их в S3-совместимое хранилище или на
локальный диск. Ожидается несколько десятков независимых выгрузок с разными
настройками, поэтому вся повторяющаяся логика уходит в провайдер, а специфика
выгрузки остаётся параметрами в DAG.

**Провайдер знает про Gmail и про то, куда положить байты. Про `.xlsx` он не знает
ничего.** Парсинг файлов и загрузка в BigQuery/PostgreSQL/ClickHouse — отдельные
слои, спроектированные позже (см. `docs/gmail-pipeline-layers-2-3.md`). Смешение
слоёв даёт «оператор, который умеет всё», с комбинаторным взрывом параметров.

Точка стыковки со следующим слоем — файл `_manifest.json`, который провайдер
пишет рядом с вложениями и путь к которому возвращает в XCom.

### Что решает

- OAuth к Gmail без хранения короткоживущего `access_token` и без записи в метабазу
- Корректный разбор MIME: кириллица в именах файлов, вложенные `multipart`, inline-картинки
- S3-режим не скачивает и не отдаёт письмо вниз повторно **даже без меток**: манифест
  с `run_id` и `message_id` в пути дают дедупликацию сами по себе — вниз каждый запуск
  уходят только письма, обработанные в этом запуске, а не всё окно. Метка
  (`mark_processed=True`) — независимая опция: чистит выдачу Gmail, экономит вызовы,
  на корректность не влияет. Подробно — в «Дедупликация» и в псевдокоде `execute()`
- Ожидание письма (сенсор) вместо падения, когда клиент не прислал отчёт

## Solution Overview

Три слоя задачи различаются скоростью изменений, и границы проведены по ней:

| Слой | Что делает | Стабильность | Где живёт |
|---|---|---|---|
| 1 | Gmail → S3 / диск | одинаков для всех выгрузок | **этот провайдер** |
| 2 | Разбор файла → таблица | самый нестабильный | вне провайдера |
| 3 | Таблица → БД/S3 | уже написан до нас | стандартные провайдеры |

Состав провайдера:

```
GmailHook                            # вся нетривиальная логика
GmailAttachmentSensor                # есть ли подходящее письмо (только Gmail)
  └─ GmailAttachmentToS3Sensor       # + bucket/prefix: есть ли письмо БЕЗ манифеста
GmailAttachmentsBaseOperator         # абстрактный: поиск, отбор, манифест, метка
  ├─ GmailAttachmentsToS3Operator    # + bucket/prefix/aws_conn_id, dedup, overwrite
  └─ GmailAttachmentsToLocalOperator # + path, без dedup, перезапись
```

Наследники операторов реализуют три метода: «записать байты», «вернуть канонический
путь по относительному» и «прочитать манифест» (`_read_manifest → Manifest | None`).
Разделение на базовый класс и наследников оправдано тем, что назначения различаются и
в записи, и в семантике дедупликации: свести это в один оператор с параметром
`destination` значит загнать разницу в ветвления внутри `execute()`. Шов оставлен
наследованием сознательно (ADR-0006), а не вынесен в порт `Destination`.

### Ключевые решения и обоснования

**`access_token` не хранится.** Хук на каждый запуск делает refresh-grant и
получает свежий токен в память. Альтернатива — писать обновлённый токен обратно в
Connection — даёт гонки между параллельными задачами, требует прав на запись в
метабазу Airflow и приводит к загадочным 401. Цена решения — один лишний HTTP-запрос
на задачу. Connection становится read-only.

**Манифест, а не листинг префикса.** Признак «письмо обработано» — существование
`_manifest.json`. Проверка непустоты префикса не годится: если задача умерла после
записи второго вложения из трёх, префикс непустой, а обработка неполная.

**Строгий порядок записи: вложения → манифест → метка.** Каждый шаг подтверждает
предыдущий. Падение между манифестом и меткой самовосстанавливается: следующий
запуск увидит письмо (метки нет), обнаружит манифест, качать не станет, просто
доставит метку.

**Скользящее окно `lookback_days`, а не привязка к `data_interval`.** Отчёт за
понедельник могут прислать во вторник вечером — при привязке к интервалу такое
письмо не попадёт ни в один запуск и потеряется навсегда.

**Метки выключены по умолчанию.** При `mark_processed=False` хватает скоупа
`gmail.readonly`, ящик не мутируется, `-label:` в запрос не подмешивается.

### Ограничение развёртывания (обязательно в README и docstring)

Провайдер написан в расчёте на **один воркер на одном сервере**.
`GmailAttachmentsToLocalOperator` пишет на локальный диск, который не разделяется
между воркерами. При переходе на CeleryExecutor с несколькими воркерами или на
KubernetesExecutor задача скачивания и задача парсинга могут уехать на разные
машины, и парсинг не найдёт файл. В таком окружении локальный оператор безопасен
только внутри одной задачи; для всего остального — S3.

## Technical Details

### Connection

```
conn_type: gmail
login:     <client_id>
password:  <client_secret>
extra:     {"refresh_token": "1//09fy...",
            "user_id": "me",
            "scopes": ["https://www.googleapis.com/auth/gmail.readonly"]}
```

Аутентификация: `google.oauth2.credentials.Credentials(token=None, refresh_token=...,
client_id=..., client_secret=..., token_uri="https://oauth2.googleapis.com/token")`
плюс `creds.refresh(google.auth.transport.requests.Request())`. Ничего никуда не
записывается.

**`userId` — обязательный параметр каждого вызова Gmail API.** Хук читает
`extra.user_id` (дефолт `"me"`) в `self.user_id` и передаёт его в `messages.list`,
`messages.get`, `attachments.get`, `labels.list`, `labels.create` и `batchModify`.
Без этого код не работает вовсе.

Для меток нужен скоуп `gmail.modify` — дописать права к существующему
`refresh_token` нельзя, его придётся перевыпустить, заново пройдя OAuth-консент.

**Поле `scopes` в `extra` декоративно.** Обновлённый токен несёт ровно те права,
которые были выданы `refresh_token` при консенте; редактирование `scopes` в
Connection ничего не меняет. Поле нужно только как документация для человека.
Реальная проверка прав — 403 `insufficientPermissions` при `batchModify`.

**Критично: OAuth-приложение должно быть опубликовано (статус «In production»).**
Если consent screen проекта остался в статусе «Testing», Google выдаёт
`refresh_token` со сроком жизни **7 дней**. Пайплайн отработает неделю и молча
сломается. Это самая частая ловушка данной схемы.

Отозванный или истёкший `refresh_token` даёт `google.auth.exceptions.RefreshError`
внутри `get_conn()` — оборачивать во внятное исключение с подсказкой, а не
пробрасывать наружу как есть.

### Сборка Gmail query

Структурированные поля склеиваются через `AND` (пробел в синтаксисе Gmail):
`from_email`, `subject_contains`, `has_attachment`, `filename_contains`.
Параметр `query` — сырая строка на языке Gmail; **если он задан, структурированные
поля игнорируются** (два источника истины недопустимы).

В обоих случаях провайдер дописывает:
- `after:<epoch_seconds>` — из `lookback_days` (либо `after:`/`before:` из явного
  диапазона `date_from`/`date_to`, см. ниже)
- `-label:"<итоговая метка>"` — только если `mark_processed=True`

**Почему epoch, а не `after:YYYY/MM/DD`.** Дату в текстовом виде Gmail трактует по
своей таймзоне, а не по нашей `Europe/Moscow`, поэтому граница окна уезжает.
Числовой `after:` принимает epoch в секундах и не оставляет места для толкований:
берём полночь `(опорный день − lookback_days)` в `timezone` оператора и переводим в epoch.
Параметр `timezone` обязан доходить до `build_query`, а не только до вычисления `dt`.

**Календарный день опорной даты берётся в `timezone` оператора** (ADR-0002).
`data_interval_end` — момент в зоне расписания DAG (у нас — UTC). Наивный
`data_interval_end.date()` берёт день в UTC; на границе суток это не тот день. Правильно:
`ref_day.astimezone(ZoneInfo(timezone)).date()`, и уже от него отсчёт `lookback_days`.
Для положительного смещения (МСК) наивная версия расширяет окно на день (дубль при
`lookback_days=0`), для отрицательного — сужает (потеря). Зону расписания DAG не читаем.

**Явный диапазон `date_from`/`date_to`** (ADR-0004, для ручного backfill). Если задан
хоть один — `lookback_days` игнорируется (WARNING, если он был не дефолтным):
`after:` = полночь `date_from`, `before:` = полночь `(date_to + 1 день)` в `timezone`
(`+1 день` — чтобы день `date_to` вошёл целиком, Gmail `before:` строго-меньше). Оба
параметра templated (из `dag_run.conf`), парсятся и валидируются в `execute()`.

**Опорный день — стабильное время `DagRun`, а не «сейчас».** Если отсчитывать окно
от текущего момента, оно уедет между попытками: письмо записано в 23:59, `mark_processed`
упал, retry стартовал в 00:01 — при `lookback_days=0` окно уже указывает на новый
день, письмо выпадает из выдачи, оператор его не находит и не возвращает манифест
текущего `run_id`. Скачанное теряется, а гарантия «retry не теряет» рушится. Поэтому
опорная дата берётся из `context` (`data_interval_end` / `dag_run.logical_date` —
стабильны между retry одной задачи) и передаётся в `build_query` явно, а не
вычисляется через `date.today()`.

`after:` **включающий** — берёт письма начиная с этого момента. Поэтому
`lookback_days` считается в календарных днях от полуночи опорного дня:

- `0` → с полуночи сегодня → **только сегодняшние** письма;
- `1` → с полуночи вчера → вчера + сегодня (два дня, а не «за сутки»);
- `7` (дефолт) → восемь календарных дней, покрывает выходные и мелкие простои.

Ноль легален. Но помните: меньшее окно легче теряет опоздавшие письма — отчёт,
пришедший в 23:59, при `lookback_days=0` доступен только до полуночи. Для источников,
которые присылают когда придётся, дефолт в неделю безопаснее.

Семантика `has_attachment`: `True` → в запрос добавляется `has:attachment`,
`False` (дефолт) → **ничего не добавляется**. Отрицание `-has:attachment` не
подставляем никогда: письмо без вложений нам всё равно не подходит, а лишний терм
только сбивает с толку.

### Отбор вложений

- `attachment_pattern: str | None` — регулярка, `re.search` по **декодированному**
  имени. Покрывает и «вхождение слова» (`отчёт`), и строгое совпадение
  (`^report_\d{8}\.xlsx$`). Отдельного параметра под подстроку не заводим.
- `filename_contains` → `filename:` в query. Это **только грубое сужение на стороне
  сервера**: Gmail не делает substring-поиск, он токенизирует имя по разделителям.
  `filename:report` найдёт `annual-report-2024.xlsx`, но не `myreport.xlsx`.
  Регулярок и wildcard в поиске Gmail нет.
- `has:attachment` врёт: логотип в подписи — тоже вложение (`image001.png`).
  Вложением считается часть с непустым `filename`. Отсекаются только inline-**картинки**:
  часть выкидывается, если она inline **и** (`mime_type` начинается с `image/`
  **или** есть заголовок `Content-ID`). Inline-PDF или inline-xlsx — отчёт, вставленный
  для показа в теле, — проходят; от лишних файлов защищает `attachment_pattern`.

  **«inline» определяется разбором заголовка, а не сравнением строки.** Реальный
  `Content-Disposition` — это `inline; filename="logo.png"` с параметрами и
  произвольным регистром. Брать первый токен до `;`, привести к нижнему регистру,
  сравнить с `inline`. Проверка `header == "inline"` пропустила бы логотипы — прямой баг.
- Тело вложения приходит **двумя способами**: обычно как `body.attachmentId`
  (качается отдельным запросом), но мелкие вложения могут прийти сразу в
  `body.data` (base64url, без `attachmentId`). Определять по **наличию ключа `data`**
  в `body`, а не по его truthiness: пустой файл даёт `data=""`, и проверка на
  истинность ошибочно ушла бы к отсутствующему `attachmentId`. Часть без обоих
  источников — не вложение.
- MIME-дерево обходится **рекурсивно** (`multipart/mixed` → `multipart/related` → …).
- `attachmentId` нестабилен между запросами: использовать сразу после
  `messages.get`, никуда не сохранять.

### Декодирование имени: сначала проверить, нужно ли оно вообще

Gmail API отдаёт `MessagePart.filename` **готовой строкой**, а не сырым заголовком
`Content-Disposition`. Если она уже нормализована сервером, то декодировать нечего:
ни RFC 2047, ни RFC 2231 в ней не будет.

Из этого следует, что `collapse_rfc2231_value()` **не годится**: он разбирает кортеж
от парсера параметров заголовка, а из одной строки continuation-параметры
(`filename*0*`, `filename*1*`) восстановить невозможно в принципе. Поэтому отдельной
функции `decode_filename` в плане нет — имя сразу идёт в `sanitize_filename`.

Базовое предположение: декодирование имени не нужно. Если фикстуры (синтетические в
Task 2, реальные — валидация в Post-Completion) вдруг покажут закодированное имя,
внутрь `sanitize_filename` добавляется защитный RFC 2047 fallback
(`email.header.decode_header`). Полноценный разбор `Content-Disposition` для имени в
план не закладываем: сырого заголовка у нас нет, а изобретать его — работа ради работы.

**Отдельно: `Subject` и `From` для манифеста** приходят в `payload.headers` как
список `{"name": ..., "value": ...}`, и вот они **закодированы по RFC 2047** —
кириллическая тема выглядит как `=?UTF-8?B?...?=`. Их декодировать нужно точно.

### Имя файла — недоверенный ввод

Декодированное имя приходит из письма, то есть его контролирует отправитель.
Перед использованием в пути оно **обязано** проходить санитизацию: взять только
basename, вырезать `/`, `\`, `..`, нулевые байты и управляющие символы; если после
этого имя пустое — подставить `attachment_<n>`. Для локального оператора это
защита от обхода пути (`../../etc/cron.d/x`), для S3 — от неожиданной структуры
ключей.

### Коллизия имён внутри одного письма

В одном письме может быть **два вложения с одинаковым именем**. Наивный путь
`<message_id>/<filename>` приведёт к тому, что второй файл затрёт первый, а
манифест будет содержать две записи, указывающие на один путь — тихая потеря
данных. При коллизии добавлять суффикс перед расширением: `report.xlsx`,
`report_1.xlsx`, `report_2.xlsx`. В манифест писать исходное имя (`name`) и
фактический путь (`path`) раздельно.

### Пути

```
<base>/dt=YYYY-MM-DD/<message_id>/<filename>
<base>/dt=YYYY-MM-DD/<message_id>/_manifest.json
```

- S3: `<base>` = `prefix` (например `gmail/avito`) внутри `bucket`
- local: `<base>` = `path` (например `/data/gmail/avito`)
- `dt` вычисляется из `internalDate` в таймзоне **`Europe/Moscow`**
  (параметр `timezone: str = "Europe/Moscow"`). `internalDate` приходит в JSON
  **строкой** с epoch в миллисекундах — не забыть `int()` и деление на 1000
- `message_id` — опаковый id письма в пределах ящика (`users.messages.list` → `id`),
  hex-строка, безопасна для пути. Не путать с RFC-заголовком `Message-ID`
  (глобальный, содержит `<>@`) и с `attachmentId`. Не хронологический.

### Манифест

Это контракт со следующим слоем, поэтому схема одна и та же во всех документах
(`docs/gmail-pipeline-layers-2-3.md` приведён к ней же) и покрыта отдельным тестом.

```json
{"source": "avito",
 "message_id": "18c2f4a9b3d5e6f7",
 "internal_date": "2026-07-10T09:14:22+03:00",
 "subject": "Отчёт за 09.07",
 "from": "reports@avito.ru",
 "run_id": "scheduled__2026-07-10T06:00:00+00:00",
 "files": [{"name": "report.xlsx", "size": 148223,
            "path": "gmail/avito/dt=2026-07-10/18c2f4a9b3d5e6f7/report.xlsx"}]}
```

- `source` — свободная метка для трассировки, в пути не участвует
- `internal_date` — ISO 8601 в `timezone` оператора (по умолчанию `+03:00`)
- `name` — исходное имя вложения до санитизации
- `path` — **канонический** путь назначения: для S3 это ключ внутри `bucket`
  (`<prefix>/dt=…`), для локального оператора — абсолютный путь на диске
- `run_id` — идентификатор `DagRun`, записавшего манифест. По нему оператор отличает
  «доставлено прошлым запуском» (вниз не отдавать) от «записано упавшей попыткой
  этого же запуска» (отдать, не качая). Слой 2 поле игнорирует
- поля `s3_key` нет: слой 2 не должен знать, откуда приехал файл

Отсюда следует, что двух абстрактных методов наследнику мало. Нужен третий:

```python
_write(rel_path: str, data: bytes) -> None       # записать
_destination_path(rel_path: str) -> str          # канонический путь для манифеста
_read_manifest(rel_dir: str) -> Manifest | None  # прочитанный Manifest, None если нет
```

Все три принимают **одну строку** — относительный путь от базы. `rel_dir` вида
`dt=2026-07-10/18c2f4a9b3d5e6f7` собирает базовый класс; наследник его не строит и
про формат `dt=` не знает. Без `_destination_path()` базовый класс не может заполнить
`files[].path` и вернуть путь манифеста в XCom. `_read_manifest()` возвращает **весь
`Manifest`** (не голый `run_id`): парсинг и валидация живут в `Manifest.from_json`, а
тристейт доставки считает чистая `decide(manifest, run_id, overwrite)` — см. модуль
`manifest.py` в `CONTEXT.md` и грилинге `/improve-codebase-architecture`. Факта «манифест
есть» мало — оператору нужно знать, **чей** он, и это решает `decide`, а не оператор.

### Метки

- `mark_processed: bool = False`
- `label_suffix: str | None = None` → `airflow/processed`;
  при `label_suffix="avito"` → `airflow/processed/avito`
- **Ловушка: вложенные метки в Gmail не иерархичны при поиске.**
  `label:airflow/processed` не находит письма, помеченные только
  `airflow/processed/avito`. Поэтому в `-label:` подставляется ровно та же итоговая
  строка, которую вешаем, всегда в кавычках.
- API работает с `labelId`, не с именем: `labels.list` → найти по имени → при
  отсутствии `labels.create` (принимает полное имя со слэшами, поля «родитель» нет).
  Кэшировать один раз за запуск задачи.
- Пачкой — `messages.batchModify` (до 1000 id за вызов).

### Устойчивость к ошибкам Gmail API

`googleapiclient` **по умолчанию не повторяет запросы**. Gmail ограничивает
250 quota units на пользователя в секунду, и при десятках выгрузок 429 —
вопрос времени. Каждый вызов выполняется как `.execute(num_retries=N)`
(встроенный экспоненциальный backoff для 429 и 5xx). Это касается `messages.list`,
`messages.get`, `attachments.get`, `labels.list/create`, `batchModify`.

`messages.list` при пустом результате **не возвращает ключ `messages`** — читать
через `.get("messages", [])`, иначе `KeyError` вместо честного «писем нет».

Одно вложение целиком загружается в память (`load_bytes`). Gmail ограничивает
входящие письма 25 МБ, так что верхняя граница ясна, но упомянуть в docstring.

### Алгоритм оператора

```
delivered, to_label = [], []
run_id     = context["run_id"]                  # стабилен между retry, свой у каждого DagRun
ref_day    = context["data_interval_end"]       # стабильная опорная дата окна, НЕ date.today()
label_name = resolve_label_name(self.label_suffix)   # airflow/processed[/<suffix>] — чистая функция (Task 4)
window     = Window.resolve(ref_day, self.timezone, self.lookback_days, date_from, date_to)
query      = hook.build_query(window, self._filter_processed_label(), label_name, <поля фильтра>, self.query)
                                                # _filter_processed_label(): S3 → всегда False (ADR-0001: метка не
                                                # фильтрует поиск, иначе retry теряет доставку); local → self.mark_processed

# Поиск, get_message, рекурсивный обход MIME, отбор по attachment_pattern и
# INFO-лог «не наше письмо» живут ВНУТРИ хука. Тем же методом пользуются оба
# сенсора — второй копии этой логики в проекте быть не должно.
for msg in hook.find_messages_with_attachments(query, pattern):
    dt         = to_local_date(msg.internal_date, self.timezone)
    rel_dir    = f"dt={dt}/{msg.message_id}"
    manifest_p = self._destination_path(f"{rel_dir}/_manifest.json")

    # overwrite=True → манифест НЕ читаем вовсе (передаём None): битый манифест не должен
    # ронять аварийное восстановление ради которого overwrite и существует (см. ниже, стр. ~536)
    manifest   = None if self.overwrite else self._read_manifest(rel_dir)   # Manifest | None
    decision   = decide(manifest, run_id, self.overwrite)  # весь тристейт ADR-0001 — в модуле
    to_label.append(msg.message_id)                        # догон метки — ВСЕГДА, ортогонально

    if decision is Decision.DELIVER_ONLY:      # манифест ЭТОГО запуска (упавшая попытка):
        delivered.append(manifest_p)           # файл на месте, вниз не доехал → отдать, не качать
        continue
    if decision is Decision.SKIP:              # манифест ПРОШЛОГО запуска: вниз не отдаём
        log.info("письмо %s обработано ранее, пропускаю", msg.message_id)
        continue

    # decision is Decision.DOWNLOAD_AND_DELIVER
    files = []
    # resolve_collisions ВОЗВРАЩАЕТ ПАРЫ (attachment, safe_name); Attachment не мутируется,
    # поля safe_name в нём нет (Task 2). Распаковываем — не обращаемся к a.safe_name.
    for attachment, safe_name in resolve_collisions(msg.attachments):   # report.xlsx, report_1.xlsx, …
        data     = hook.download_attachment(msg.message_id, attachment)   # data или attachment_id
        rel_path = f"{rel_dir}/{safe_name}"
        self._write(rel_path, data)
        files.append(FileEntry(name=attachment.filename,     # исходное имя, до санитизации
                               size=len(data),           # фактический размер записанных байт
                               path=self._destination_path(rel_path)))

    manifest = Manifest.build(self.source, msg.message_id,
                              to_local_iso(msg.internal_date, self.timezone),  # ISO, зона оператора
                              msg.subject, msg.from_, files, run_id)
    self._write(f"{rel_dir}/_manifest.json", manifest.to_json())   # манифест последним
    delivered.append(manifest_p)

if mark_processed and to_label:
    hook.mark_processed(to_label, label_name)   # внутри: get_or_create_label(label_name) → labelId (Task 6)

if not delivered:
    raise AirflowSkipException("новых писем нет")
return delivered                                # → XCom: только письма ЭТОГО запуска
```

Вниз уходят **только письма, обработанные в этом запуске** — то, что реально скачано
сегодня, плюс то, что скачано упавшей попыткой этого же запуска. Вчерашние письма с
чужим `run_id` в XCom не попадают: они уже прошли через слой 2 в свой день, и гонять
их повторно незачем — иначе манифест не имел бы смысла.

Различение держится на `run_id`, потому что «манифест есть» само по себе двусмысленно:

- **Прошлый `run_id`** → письмо доставлено в один из прошлых дней окна → вниз не
  отдаём. Это то, ради чего манифест и `message_id` в пути вообще нужны.
- **Текущий `run_id`** → манифест записан этой же задачей в упавшей попытке, а
  downstream его не видел (упавшая попытка **не пушит return-XCom вообще** — чистить
  нечего, это и есть инвариант; см. ADR-0001). Файл не перекачиваем, но путь вниз
  отдаём — иначе полностью скачанное письмо потерялось бы тихо, при зелёной задаче.
- **Манифеста нет** → качаем и отдаём.

Итог: для S3 повторов доставки нет даже **без меток** — манифест + `message_id` в
пути дают дедупликацию сами по себе.

**Критично (ADR-0001): в S3-режиме `-label:` НЕ добавляется в поисковый запрос.**
Проставление метки (`batchModify`) и запись return-XCom **не атомарны**: если метка
уже проставлена, а задача упала до успешного возврата, то на retry поиск с `-label:`
**не нашёл бы** это письмо — его манифест текущего `run_id` до `decide` не дошёл бы, и
полностью скачанное письмо тихо пропало бы при зелёном retry (то же и при частичном
`batchModify`: первая пачка помечена, вторая упала). Поэтому в S3 корректность держит
**только** манифест + `run_id`, а `-label:` как фильтр поиска не используется вообще.
`mark_processed=True` в S3 по-прежнему может **вешать** метку (внешний маркер), но она
не подмешивается в запрос и на доставку не влияет — а раз не влияет, то и частичный
`batchModify` перестаёт быть проблемой корректности.

Три места, где легко разойтись с контрактом:

- `_read_manifest(rel_dir)` принимает **одну** строку и возвращает `Manifest | None`.
  Базовый класс сам собирает `rel_dir` из `dt` и `message_id`; наследник получает
  готовый относительный путь и лишь читает байты + `Manifest.from_json` (или `None`).
  Тристейт доставки считает `decide(manifest, run_id, overwrite)`, а не оператор.
- `size` берётся как `len(data)` **после** декодирования — это фактический размер
  записанных байт, не зависящий от того, что заявил сервер.
- Когда `attachment_pattern` не задан, подходят все вложения (кроме inline).
  Проверку на `None` делает хук, а не оператор.

**Локальный оператор** к этому не причастен: манифест он не читает (`_read_manifest`
всегда `None` → `decide` всегда `DOWNLOAD_AND_DELIVER`), всегда качает и всегда отдаёт
вниз всё найденное за окно. Дедупликации
там нет by design — см. «Дедупликация: разная у наследников».

### Семантика «не наше письмо»

Письмо прошло фильтр поиска, но ни одно вложение не совпало с `attachment_pattern`
→ манифест не пишем, метку не вешаем, письмо остаётся невидимым для состояния.

Цена: такое письмо перепроверяется каждый запуск, пока не выпадет из окна
`lookback_days`. Это дёшево, но опасно тем, что переименованный файл
(`report_20260710.xlsx` → `report-2026-07-10.xlsx`) даёт зелёную задачу без данных.
Поэтому лог уровня INFO с перечислением реальных имён вложений — обязательный
элемент, а не украшение.

### Сенсоры: их два, и они отвечают на разные вопросы

Один сенсор здесь не справляется. Вопрос «есть ли подходящее письмо» и вопрос «есть
ли **новая** работа» — разные, и при `mark_processed=False` они расходятся: письмо
остаётся в выдаче Gmail до конца окна `lookback_days`, поэтому сенсор, знающий только
про Gmail, будет срабатывать каждый раз, а оператор следом честно скипнется.

**`GmailAttachmentSensor`** — «есть ли подходящее письмо». Смотрит только в Gmail:
`poke()` → `True`, если `hook.find_messages_with_attachments()` непусто. Состояния
хранилища не знает. Пригоден там, где дедупликация обеспечена самим Gmail —
`mark_processed=True` (метка убирает обработанные из выдачи). Это же основной сенсор
для локального оператора. **Не полагайтесь на `lookback_days=1`**: обработанное письмо
остаётся в выдаче до конца окна, и сенсор при выключенных метках срабатывает повторно.

**`GmailAttachmentToS3Sensor`** — «есть ли новая работа». Наследует первый, добавляет
`aws_conn_id`, `bucket`, `prefix` и отбрасывает письма, для которых `_manifest.json`
уже лежит в S3. `True` только если осталось хотя бы одно необработанное письмо.
Согласован с `GmailAttachmentsToS3Operator` по определению.

Общее для обоих:

- `mode="reschedule"` — **выставляется в `__init__` по умолчанию**, а не только
  упоминается в docstring. В дефолтном `poke` сенсор держит слот воркера всё время
  ожидания (часы), при десятках выгрузок выест пул целиком.
- `soft_fail=True` → таймаут даёт `skipped`, DAG зелёный; `False` → падает и алертит.
  Параметр из `BaseSensorOperator`, писать не надо — только задокументировать.
- Состояние между сенсором и оператором не передаётся: оператор ищет заново, иначе
  фиксируем устаревший снимок. Письмо, пришедшее в зазоре, просто заберётся тоже.

Цена storage-aware сенсора: на каждом `poke` он повторяет поиск и разбор MIME, плюс
делает `check_for_key` по каждому кандидату. При `poke_interval=30 мин` это
пренебрежимо, но именно поэтому дешёвый Gmail-сенсор остаётся отдельным классом.

### Дедупликация: разная у наследников

Параметр `overwrite: bool = False` объявлен в **базовом** классе (default `False`),
чтобы `execute()` мог на него ссылаться единообразно. У локального оператора он
всегда `False` и в пользовательский интерфейс не выводится — там перекрывать нечего
(`_read_manifest` всегда `None`, файлы и так перезаписываются).

- **S3**: дедуплицирует по манифесту с `run_id` (см. псевдокод `execute()`). Письмо
  с манифестом **прошлого** запуска вниз не отдаётся и не качается; с манифестом
  **текущего** запуска (упавшая попытка) — отдаётся, но не качается; без манифеста —
  качается и отдаётся. `overwrite=True` — для принудительной перекачки (файл побился,
  манифест кривой).

  **`overwrite=True` несовместим со storage-aware сенсором.** `GmailAttachmentToS3Sensor`
  отбрасывает письма с манифестом и вернёт «работы нет» — оператор за ним просто не
  запустится. Поэтому переигрывание через `overwrite=True` запускается **без**
  `GmailAttachmentToS3Sensor` (вручную, или отдельным backfill-DAG без сенсора, или
  с обычным `GmailAttachmentSensor`). Это ограничение задокументировано и покрыто
  DAG-тестом.

  **`-label:` в S3-запрос не подмешивается вообще** (см. «Различение держится на
  `run_id`» выше): проставление метки и запись return-XCom не атомарны, поэтому фильтр
  по метке тихо терял бы письмо на retry. Корректность S3 держит только манифест +
  `run_id`. Как следствие, вопрос «overwrite снимает `-label:`» в S3 не возникает —
  снимать нечего; `overwrite` влияет лишь на чтение манифеста (при `True` не читается).
  `mark_processed=True` в S3 может вешать метку как внешний маркер, но на поиск и
  доставку не влияет.

  **Запись всегда идёт с `replace=True`.** У `S3Hook.load_bytes()` дефолт
  `replace=False`, то есть повторная запись существующего ключа падает. Это ломает
  сразу две вещи: перезапуск после падения посреди вложений (часть ключей уже есть)
  и сам `overwrite`. Решение о том, писать ли письмо, оператор принимает **раньше**,
  по манифесту; на уровне записи байтов колебаться уже не нужно.

  **Проверка манифеста не атомарна и не защищает от параллельных запусков.**
  `_read_manifest()` → запись — это классический check-then-act: два пересекающихся
  `DagRun` одной выгрузки могут оба не увидеть манифест и оба скачать письмо и
  отдать его вниз. «Один сервер» не означает «один активный запуск». Поэтому гарантия
  формулируется честно: **нет повторов при последовательных запусках**, а от
  параллельных защищает DAG — `max_active_runs=1` (в примере DAG это выставлено и
  прокомментировано). Это ограничение уровня DAG, а не оператора.

- **Local**: пользовательского аргумента `overwrite` в публичной сигнатуре нет —
  но атрибут `self.overwrite` существует (объявлен в базе, всегда `False`; см. выше),
  чтобы базовый `execute()` ссылался на него единообразно без `AttributeError`.
  `_read_manifest()` всегда `None`.
  Оператор качает всё, что вернул поиск, **перезаписывает файлы, не проверяя их
  наличие**, и отдаёт вниз всё найденное за окно. Локальный диск эфемерен и не хранит
  состояние между запусками; в штатном сценарии («скачал → распарсил → таск-уборщик
  снёс») файлов там и не должно быть, а если запуск всё же повторился — перезапись
  безопаснее, чем падение. Манифест всё равно пишется как описание скачанного для
  следующего шага (с `run_id`, хоть локальный оператор его и не читает).

  **`-label:` — только локальный опт-ин для широких окон.** Штатный безопасный паттерн
  local — `lookback_days=0` (только сегодня), там метка не нужна: письмо и так в одном
  запуске. Если пользователь берёт широкое окно и `mark_processed=True`, `-label:`
  снижает повторную доставку. Честная оговорка (в docstring): падение между
  проставлением метки и доставкой вниз может на retry «потерять» доставку такого письма
  — приемлемо в рамках уже задокументированной неидемпотентности local, но именно
  поэтому в S3 (где есть контракт retry-доставки) `-label:` как фильтр не применяется.

  Дедупликация в локальном режиме возможна **только через `mark_processed=True`** —
  метка убирает письмо из выдачи Gmail. `lookback_days=1` дедупликацией **не является**:
  окно поиска — это фильтр по времени, а не состояние обработки; письмо будет
  находиться в каждом запуске, пока не выпадет из окна. Меньшее окно лишь уменьшает
  число повторов, не устраняет их.

Уборка локальных файлов — задача DAG'а (отдельный таск на `all_done`), не оператора.
Оператору всё равно, что будет с файлом дальше. В docstring предупредить про
забивание диска.
