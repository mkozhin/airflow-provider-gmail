# ADR-0001: Контракт доставки слоя 1 — письма текущего запуска, переживающие retry

- **Статус:** Accepted
- **Дата:** 2026-07-11

## Контекст

Слой 1 скачивает вложения из писем и кладёт их в S3 или на локальный диск, затем
передаёт результат следующему таску (слою 2). В одном письме несколько вложений,
каждое качается отдельным запросом; запросы к Gmail и записи в хранилище могут падать.
Нужно определить, **что именно** слой 1 гарантирует потребителю вниз.

Ключевой сценарий (со слов заказчика): часть вложений скачалась, часть — нет; задача
падает и перезапускается retry. На выходе вниз должны уйти **все** файлы, обработанные
в этом запуске, а не только добранные последним retry.

## Решение

**Слой 1 отдаёт вниз (в XCom, списком путей к манифестам) ровно те письма, которые
скачаны и сохранены в этом запуске — включая скачанные упавшей попыткой того же
запуска. Retry не теряет уже сохранённое.** Вчерашние письма с чужим `run_id` вниз не
отдаются.

Механизм — различение по `run_id` (см. `CONTEXT.md`):

- манифест **текущего** `run_id` (упавшая попытка) → путь вниз, файлы не перекачиваются;
- манифест **прошлого** `run_id` → вниз не идёт;
- манифеста нет → качаем и отдаём.

Гранулярность — **на письмо**. Манифест пишется после всех вложений письма. Падение
внутри письма (часть вложений скачана) манифест не пишет → на retry письмо качается
**целиком заново**. Пофайлового состояния внутри письма нет: при лимите Gmail 25 МБ и
редкости retry перекачка целого письма дешевле, чем хранить частичное состояние.

Точная мысленная модель (важно для сопровождения): ветку «текущий `run_id` → отдать
вниз» держит **не** «Airflow чистит XCom», а то, что **упавшая попытка не пушит
return-XCom вообще** — downstream её результата не видел, файлы на S3 есть, значит вниз
их надо доставить на retry, иначе тихая потеря при зелёной задаче.

## Consequences

- Манифест обязан быть **на письмо** и нести `run_id`; чтение манифеста ради `run_id` —
  один лишний GET на письмо в окне (S3).
- **В S3-режиме метка (`-label:`) НЕ используется как фильтр поиска.** Проставление метки
  (`batchModify`) и запись return-XCom не атомарны: если метка проставлена, а задача упала
  до успешного возврата, то на retry поиск с `-label:` не нашёл бы письмо, его манифест
  текущего `run_id` не дошёл бы до `decide`, и полностью скачанное письмо тихо потерялось
  бы при зелёном retry (то же — при частичном `batchModify`). Поэтому корректность S3
  держит **только** манифест + `run_id`; `mark_processed=True` в S3 может вешать метку как
  внешний маркер, но в запрос она не подмешивается. Реализация: `_filter_processed_label()`
  → `False` у S3-оператора и S3-сенсора, `mark_processed` — у local/Gmail-сенсора.
  *(Правит прежнюю формулировку «метка на корректность дедупликации не влияет»: она влияла —
  через фильтр поиска — и именно поэтому фильтр в S3 снят.)*
- `execute()` потребляет `hook.find_messages_with_attachments()` и строит доставку по
  `run_id`; порядок «вложения → манифест → метка» — часть контракта.
- Запись всегда с перезаписью (`replace=True` в S3, overwrite на диске): перекачанное
  на retry вложение **переписывает** прошлую копию, дубля байтов в хранилище нет.
- Локальный режим в этот контракт **не входит**: манифест не читает, качает и отдаёт
  вниз всё найденное за окно каждый запуск.

### Рамка дублей — решено (вариант B)

Downstream идемпотентным **не считается**. Система устроена так, что в штатном пути
каждое письмо доставляется вниз один раз:

- **S3** — дедуп доставки по манифесту + `run_id` (см. Решение). Подавление
  past-`run_id` — оптимизация нагрузки на слой 2, а не гарантия корректности:
  корректность держит сам факт «вниз идут только письма этого запуска».
- **Локальный** — безопасный паттерн: `lookback_days=0` (только сегодня) + ежедневный
  запуск + сенсор, ждущий письмо. При окне «только сегодня» письмо попадает ровно в один
  дневной запуск. Дубли гасятся **узостью окна**, а не дедупом.

Следствия для API и документации:

- **Локальный оператор переопределяет дефолт `lookback_days` на `0`** (у S3 остаётся
  `7`). Разные дефолты отражают разную семантику: у S3 широкое окно безопасно (дедуп),
  в локальном — размножает доставку. Это идёт в docstring.
  *Реализовано в плане: split-default заложен в Task 7b и Task 10.*
- Широкое окно в локальном режиме или `overwrite=True` в S3 — единственные пути,
  где дубли возможны; они opt-in и документируются как таковые.
