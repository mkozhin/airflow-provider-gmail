# ADR-0002: Календарный день окна вычисляется в таймзоне оператора

- **Статус:** Accepted
- **Дата:** 2026-07-11

## Контекст

Окно поиска — `after:<epoch>`, где epoch = полночь `(опорный день − lookback_days)`.
Опорный момент берётся из `context["data_interval_end"]` — это tz-aware datetime **в зоне
расписания DAG**. В текущем окружении расписание DAG задано в **UTC**, а бизнес-зона
данных — **Europe/Moscow** (параметр оператора `timezone`, дефолт `Europe/Moscow`).

Вопрос: в какой зоне брать **календарный день** у `data_interval_end` перед отсчётом
`lookback_days`. Наивный `data_interval_end.date()` берёт день в зоне расписания (UTC),
а не в бизнес-зоне.

## Решение

Оператор вычисляет день окна в **своей** зоне `timezone`, зону расписания DAG не читает:

```
ref_local  = data_interval_end.astimezone(ZoneInfo(self.timezone))
window_day = ref_local.date() - timedelta(days=lookback_days)
after_epoch = int(datetime(window_day, tzinfo=ZoneInfo(self.timezone)).timestamp())  # полночь
```

`timezone` — параметр оператора; каждая выгрузка объявляет свою бизнес-зону сама
(«у других выгрузок она может быть иной»). Отдельный DAG-level параметр не вводится.

## Consequences

- Робастно к любой зоне расписания DAG (в нашем окружении — UTC).
- **Знак ошибки при наивной реализации.** Для положительного смещения (МСК = UTC+3)
  МСК-дата ≥ UTC-даты, поэтому наивный `.date()` даёт окно **шире** на день (начинается
  раньше), а не уже. `after:` — только нижняя граница, значит следствие — **лишний день**,
  а не потеря:
  - **Локальный `lookback_days=0`** → отдаёт вниз **два дня** вместо одного → рушит
    свойство «один раз» из ADR-0001.
  - **S3** → лишнее письмо в проверке, дедуп по `run_id` его гасит (безвредно).
  - **Отрицательное смещение** (не наш случай, но провайдер общий) → окно **уже** →
    ранние письма выпадают → **потеря**. Ещё причина чинить безусловно.
- Ошибка **детерминирована по расписанию**: cron'ы, чей `data_interval_end` попадает в
  вечерний UTC-бэнд (21:00–23:59 UTC = 00:00–02:59 МСК), промахиваются всегда; утренние
  UTC-cron'ы — никогда (UTC-дата и МСК-дата совпадают).

## Тест (в плане)

Помимо теста «epoch = **полночь МСК, а не UTC**» (доля суток), в плане есть отдельный
тест на **выбор дня** (Task 4, `tests/test_window.py`):
`ref_day = 2026-07-11 22:00:00+00:00`, `timezone="Europe/Moscow"` →
день окна `2026-07-12` (МСК-день), а не `2026-07-11` — ловит наивный `ref_day.date()` в UTC.
