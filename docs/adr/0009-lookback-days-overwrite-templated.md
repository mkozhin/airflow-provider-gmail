# ADR-0009: `lookback_days`/`overwrite` templated, строгий фолбэк

- **Статус:** Accepted
- **Дата:** 2026-07-30

## Контекст

`lookback_days` был обычным аргументом `__init__` (оператор + сенсор),
валидируемым (`validate_lookback_days`) в момент парсинга DAG. `overwrite`
(оператор) был обычным аргументом `__init__`, но не валидировался вообще —
принималось любое python-значение как есть. Ни то, ни другое не входило в
`template_fields`, так что параметры Airflow (`dag_run.conf`/Jinja) до них не
долетали: разово расширить окно поиска или разово прогнать backfill можно было
только правкой и передеплоем файла DAG.

`date_from`/`date_to` уже решают ровно этот класс проблемы (ADR-0004): они
templated и парсятся *после* рендеринга, в `execute()`/`poke()`, а не в
`__init__`. Симметрия с этим решением — прямой прецедент для `lookback_days`.

Контраст — `attachment_pattern` (ADR-0005): он сознательно **не** templated,
компилируется в `__init__`, потому что `template_fields` рендерятся
непосредственно перед `execute()`, перезаписывая атрибут — компиляция в
`__init__` пришлась бы на сырую строку с `{{ ... }}`. Это решение здесь не
пересматривается; `lookback_days`/`overwrite` попадают в ту же ловушку (каст
в `__init__` увидел бы шаблон), поэтому для них выбран тот же путь, что и для
`date_from`/`date_to` — каст/валидация в рантайме, а не в `__init__`.

## Решение

`lookback_days` (оба класса операторов, оба класса сенсоров) и `overwrite`
(базовый + S3-оператор) становятся `template_fields`. Аннотации `__init__`
расширяются до `int | str` / `bool | str`; сам `__init__` каст/валидацию
больше не выполняет — присваивает атрибут как есть.

Каст и валидация вынесены в `dates.py`:

- `resolve_lookback_days(value: int | str | None) -> int` — каст к `int`,
  отклонение отрицательных;
- `resolve_overwrite(value: bool | str | int | None) -> bool` — нативный
  `bool` проходит насквозь; строки `"true"/"1"` / `"false"/"0"`
  регистронезависимо; нативный `int` `0`/`1` (покрывает
  `render_template_as_native_obj=True`); всё остальное — `ValueError`.

Обе функции вызываются безусловно в начале `_run()` (оператор) и
`_find_messages()` (сенсор) — после рендеринга шаблонов, до любого
использования значения — и результат используется через локальную переменную;
`self.lookback_days`/`self.overwrite` не мутируются.

**Фолбэк строгий**: рендер в пустую строку, `None` (нативный,
`render_template_as_native_obj=True`) или буквальную строку `"None"`
(классическая ловушка `{{ dag_run.conf.get('x') }}`, когда ключа нет) —
`ValueError`, а не тихая подстановка дефолта класса. Ответственность за
дефолт лежит на самом Jinja-выражении (`{{ dag_run.conf.get('lookback_days',
7) }}`), не на резолвере.

**Типы, которые тихо исказили бы результат, отклоняются явно**, а не
округляются:

- нативный `bool` для `lookback_days` — `ValueError`: `int(True) == 1` иначе
  тихо превратил бы нативно отрендеренный `true` в однодневное окно;
- нативный `float` (в т.ч. «целый» `3.0`) для `lookback_days` — `ValueError`:
  `int(1.9) == 1` иначе тихо сузил бы окно вместо явного отказа; нативный
  Jinja может вернуть `float` из арифметического выражения в `dag_run.conf`;
- порядок проверок в `resolve_overwrite` — `isinstance(value, bool)` **до**
  `isinstance(value, int)` обязателен, поскольку в Python `bool` — подкласс
  `int`.

**Название `resolve_`** (а не `parse_`, как у `parse_date_range`) выбрано
осознанно: в отличие от `parse_date_range`, которая лишь парсит ISO-текст в
`date`, эти две функции дополнительно применяют *политику* (отклонить
отрицательное / отклонить неоднозначную истинность) — ближе к тому, как
`Window.resolve` и `resolve_label_name` уже используют «resolve» в смысле
«превратить сырой вход в единственное конкретное значение, которым дальше
пользуется код».

Валидация `lookback_days`, ранее выполнявшаяся `validate_lookback_days` в
`__init__`, удалена без deprecated-обёртки — единственные вызывающие были
внутри пакета (оператор, сенсор), оба мигрированы на `resolve_lookback_days`.

## Consequences

- **В скоупе**: `lookback_days` (оператор + сенсор) и `overwrite` (оператор).
  **Задел** (сознательно не реализуется здесь, фиксируется как область для
  будущего плана): `timezone`, `has_attachment`, `mark_processed`,
  `label_suffix`. `attachment_pattern` остаётся сознательно не templated по
  ADR-0005 — это решение здесь не пересматривается.

- **Изменение точки отказа (`lookback_days`)**: невалидный литерал (например
  `lookback_days=-1`, переданный обычным python-значением без всякого Jinja)
  раньше падал в момент парсинга DAG (`__init__`); теперь падает на
  `execute()`/первом `poke()`. Это прямое следствие того, что один и тот же
  рантайм-путь теперь обслуживает и литерал, и шаблон — раздельного пути «это
  точно литерал, валидируй сразу» не сохраняется, ради простоты одного места
  каста.

- **Вновь введённая валидация (`overwrite`)**: раньше `overwrite` не
  валидировался вообще — принималось любое значение, и оно использовалось по
  «правдивости» (`None if self.overwrite else ...`). Теперь оно строго
  валидируется через `resolve_overwrite`. Отдельно — краевой случай реальной
  обратной несовместимости: `overwrite=None` сегодня молча работает как
  `False` (`None` falsy), а `resolve_overwrite(None)` кидает `ValueError`.
  Реалистичный сценарий — DAG, пишущий `overwrite=some_dict.get("overwrite")`
  без всякого Jinja: раньше отсутствие ключа тихо давало `False`, теперь
  падает. Решение — не подстраивать `None` под тихий `False`: это подорвало
  бы весь смысл строгого фолбэка для templated-случая, где `None` — самый
  частый мусорный рендер (`{{ dag_run.conf.get('overwrite') }}` без дефолта).
  Несовместимость принята осознанно, а не как недосмотр.

- **Безусловный каст**: `resolve_lookback_days`/`resolve_overwrite`
  выполняются в начале `_run()`/`_find_messages()` даже в режиме явного
  диапазона (`date_from`/`date_to` заданы), где `Window.resolve` в итоге
  игнорирует `lookback_days` полностью (ADR-0004). Шаблонизированный
  `lookback_days`, отрендерившийся в мусор, всё равно падает — даже когда его
  значение семантически не повлияло бы на этот конкретный запуск. То же самое
  для `overwrite` на локальном операторе: `_read_manifest()` там всегда
  возвращает `None` независимо от `overwrite`, но `resolve_overwrite` всё
  равно должен успешно отработать, иначе исключение. Это осознанное следствие
  каста один раз в начале метода — простота важнее точности — а не
  недоглядка.

- **Существующий пробел с проброс `overwrite` через `kwargs` у локального
  оператора — не закрыт этим планом.** `GmailAttachmentsToLocalOperator.__init__`
  не объявляет `overwrite` в собственной сигнатуре, но пробрасывает `**kwargs`
  в `super().__init__(...)`, который `overwrite` принимает — это
  задокументированный, но не новый пробел (существовал и до этого плана).
  После шаблонизации `overwrite` на базовом классе DAG-автор, обнаруживший
  этот проброс, может передать туда и Jinja-строку для локального оператора;
  `resolve_overwrite` всё равно выполнится и упадёт на невалидном
  отрендеренном значении, хотя для этого класса результат каста никогда не
  влияет на поведение (`_read_manifest()` всегда `None`). Явно вне скоупа
  этого плана.

- **Шаблонизация `overwrite` обостряет существующую ловушку
  «`overwrite` несовместим с `GmailAttachmentToS3Sensor`»** (README.md,
  докстринги S3-оператора/S3-сенсора): раньше несовместимое сочетание было
  видно прямо в коде DAG (`overwrite=True` — литерал). Теперь DAG с этим
  сенсором и templated `overwrite` может тихо встать в deadlock от одного
  изменения значения в `dag_run.conf`, без единой правки самого файла DAG.

- **Удаление `validate_lookback_days` без deprecated-обёртки — потенциально
  breaking change для внешнего кода**, который мог импортировать её напрямую
  (`from airflow_provider_gmail.dates import validate_lookback_days`).
  Grep по репозиторию доказывает отсутствие только *внутренних* потребителей,
  не внешних. Обоснование, почему это принято без shim'а: у
  `operators/gmail.py` уже есть курируемый список ре-экспорта `__all__`,
  который явно включает `parse_date_range`, `resolve_collisions`,
  `to_local_date`, `to_local_iso` из `dates.py`/`window.py`, но никогда не
  включал `validate_lookback_days`/`validate_timezone`/`resolve_lookback_days`/
  `resolve_overwrite` — то есть эти функции уже были осознанно исключены из
  курируемой публичной поверхности пакета, а не просто «случайно публичны»
  из-за отсутствия `_`-префикса. Отмечено в CHANGELOG как потенциально
  breaking для прямых импортов, а не как внутренний рефакторинг.
