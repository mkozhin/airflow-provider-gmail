# ADR-0008: `pick="all"` сортирует по возрастанию `internal_date`

- **Статус:** Accepted
- **Дата:** 2026-07-30

## Контекст

`GmailResolveAttachmentsOperator`/`resolve_attachments()` с `pick="all"`
отдавали вложения **в порядке входного списка `manifests`** — то есть в
порядке, в котором Gmail API вернул письма при поиске / в порядке, в котором
download-оператор их обработал. Gmail не гарантирует `messages.list` в
хронологическом порядке, и код никак не сортировал результат — совпадение
входного порядка с хронологией писем было артефактом, а не контрактом.

Downstream-потребитель (например `airflow-provider-tablefile`), получая
список путей через XCom, ожидает обрабатывать их в реальном хронологическом
порядке писем. Данных для этого достаточно уже сейчас: `internal_date` —
обязательное строковое поле манифеста с самого начала схемы (Task 2c),
хранится с точностью до миллисекунды (`to_local_iso`/`from_local_iso`,
`dates.py`), новый вызов Gmail API не нужен, схема манифеста не меняется.

## Решение

`_resolve()`, ветка `pick == "all"`, сортирует пары `(manifest_path,
Manifest)` по возрастанию `internal_date` — самое старое письмо первым,
сравнение как aware `datetime` через `from_local_iso` (тот же парсер, что уже
использует `pick="latest"`), никогда не лексикографически по ISO-строке.
Манифесты с равным `internal_date` (включая дублирующийся манифест на входе)
разрешаются **стабильной сортировкой** (`sorted()` в Python гарантированно
стабилен) — порядок между ними остаётся как во входном списке, без явного
вторичного ключа по `message_id`. Файлы **внутри** одного манифеста
(`files[]`) не переупорядочиваются — сортируются только манифесты между
собой. `pick="latest"` не меняется.

Побочный эффект: сортировка **перегруппирует** вперемешку расположенные
дубли одного и того же манифеста — раньше `[A, B, A]` оставался `[A, B, A]`,
теперь при `internal_date(A) < internal_date(B)` становится `[A, A, B]`.
Дубликаты по-прежнему проходят как есть **по количеству**, но не гарантируют
исходную **позицию**.

Малформед `internal_date` (например naive-строка без offset) при
`pick="all"` теперь поднимает `ValueError` из `from_local_iso` — раньше
`pick="all"` вообще не читал и не парсил `internal_date`.

## Обоснование

Рассматривались четыре варианта:

- **Опциональный флаг сортировки** (например `sort_by_date=True`),
  сохраняющий старое поведение `pick="all"` по умолчанию — отклонён: плодит
  комбинации `pick`×`flag`, а старое поведение ("в порядке входного списка")
  не имеет ни одного обоснованного случая использования, который стоило бы
  сохранять.
- **Новый режим `pick`** (например `pick="all_by_date"`) — отклонён: два
  способа получить "все вложения" — источник путаницы, а не польза;
  хронологический порядок должен быть *единственно разумным* значением по
  умолчанию для `"all"`.
- **Сортировка на стороне потребителя** (downstream DAG сортирует сам по
  `internal_date` из манифеста) — отклонена: заставляет каждого потребителя
  дублировать логику, которая и так уже есть в резолвере (он читает
  манифесты и знает `internal_date`), нарушая роль резолвера как
  единственного клиента контракта манифеста (`resolve.py` — "official
  client" `_manifest.json`-слоя).
- **Прямой BREAKING** (выбранный вариант) — единственно оправданный:
  pre-1.0 провайдер, единственный реальный кейс использования
  (хронологический порядок), прецедент `[0.3.0]` (там XCom-контракт уже
  ломали без флага защиты).

Отдельно рассматривалась и отклонена **альтернатива tie-break по
`message_id`** (симметрично `pick="latest"`, `resolve.py:93-96`) — обсуждена
в двух раундах ревью (codex + `planning:plan-review`) и подтверждена
пользователем: `internal_date` хранится с точностью до миллисекунды,
вероятность двух разных писем с идентичной меткой практически нулевая —
остаточная недетерминированность стабильной сортировки при коллизии дат
(порядок в этом крайнем случае определяется входным списком) — осознанный,
принятый trade-off, а не забытый случай.

## Consequences

- **BREAKING** для существующих потребителей `pick="all"`: порядок вывода
  меняется с "как во входном списке" на "хронологически по `internal_date`".
  Перед выпуском новой версии нужно проверить DAG-и в проде на неявные
  зависимости от старого порядка.
- Новый источник отказа: манифест с битым/наивным (без offset) `internal_date`
  теперь роняет `pick="all"` с `ValueError` из `from_local_iso` — раньше эта
  ветка вообще не читала поле.
- Вперемешку расположенные дубли одного манифеста **перегруппировываются**
  сортировкой — количество копий сохраняется, позиция — нет; README/README_RU/
  CONTEXT.md фиксируют это уточнение рядом с "дубликаты проходят как есть".
  Будущим обзорам: не путать это с дедупликацией — резолвер по-прежнему не
  удаляет дубликаты, только переупорядочивает их вместе с остальными
  манифестами.
