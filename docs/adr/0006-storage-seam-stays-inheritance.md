# ADR-0006: Шов хранилища остаётся наследованием; порт `Destination` не выделяем

- **Статус:** Accepted
- **Дата:** 2026-07-11

## Контекст

Грилинг `/improve-codebase-architecture` предложил вынести шов S3/Local (методы
`_write`, `_destination_path`, чтение манифеста) из иерархии операторов в отдельный
объект `Destination`, который оператор держит по композиции (публичные классы операторов
остаются тонкой проводкой). Это самое естественное «углубление» шва, и будущие
архитектурные обзоры будут его переоткрывать.

## Решение

Шов хранилища **остаётся** тремя protected-методами на иерархии
`GmailAttachmentsBaseOperator → {ToS3, ToLocal}`. Отдельный порт `Destination` **не**
выделяем.

## Обоснование

- Единственный ощутимый выигрыш от `Destination` — **прямая тестируемость шва** без
  операторного каркаса (in-memory `DictDestination` вместо фейк-субкласса + S3-моков).
  Всё остальное (единый `execute()`, вариативность за портом) уже обеспечено базовым
  классом: `execute()` и так один, наследники уже тонкие.
- Тестируемости **одной** недостаточно против цены: лишняя косвенность и объект-порт
  там, где Airflow-разработчик ожидает один оператор-класс на назначение
  (`template_fields`, UI-класс на выгрузку — норма экосистемы).
- Тест удаления даёт лишь слабое «да»: без `Destination` три метода возвращаются на
  класс, но сложность не взрывается — переезжает обратно.

## Consequences

- Будущим архитектурным обзорам: **не** пере-предлагать порт `Destination` ради
  тестируемости — это ре-литигация. Пере-открывать только если появится **третий**
  адаптер хранилища (тогда «два адаптера = гипотетический шов» станет тремя, и
  композиция начнёт окупаться самостоятельно).
- Чистый модуль `Manifest` (принят отдельно) от этого не страдает: чтение остаётся
  protected-методом `_read_manifest(rel_dir) -> Manifest | None` на наследнике
  (S3 парсит через `Manifest.from_json`, local → `None`).
